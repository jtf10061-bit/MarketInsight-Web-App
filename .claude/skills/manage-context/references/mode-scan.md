# モード 2: 既存リポ読み取り作成

既存リポジトリをスキャンし、CLAUDE.md と docs/ 配下を **サブエージェント逐次起動** で一括生成する。

## 前提

- `.claude/`（agents / rules / skills / settings.json）は本テンプレリポから単純コピーで持ち込まれている前提
- 本フローの責務は **CLAUDE.md と docs/ 生成のみ**
- `.claude/skills/workflow-config.md` の設定は **責務外**（触らない）

## ステップ 1: リポジトリスキャン + 結果提示

サブエージェント（Read / Glob / Grep / Bash 可）に以下の項目を抽出させ、検出結果を一覧でユーザーに提示して誤り・不足を確認する。探索手順は agent に委ねる。ヒット 0 件の項目は未確定としてユーザーに直接質問する。

抽出 + 提示項目:

- **技術スタック**: 言語・フレームワーク・主要ライブラリ（モノレポ・サブディレクトリ構成も考慮）
- **ビルド / テスト / lint / format コマンド**: マニフェストの scripts・タスクランナー・CI 設定から
- **ディレクトリ構成**: gitignore 反映済みのツリー（深さ 2-3、ノイズ除外）
- **リンター・フォーマッター設定**: 設定ファイル + pre-commit
- **ブランチ構成**: リモート / 現在ブランチ・命名規則
- **LLM / エージェント関連の有無**: LLM SDK 依存・`prompts/` `agents/` `tools/` 等のディレクトリ・典型シンボル（`@tool` / `system_prompt` 等）の頻度。すべて 0 件なら `agent-design.md` は status: not-applicable 扱い

モノレポ・非定型構成・git 未管理・IaC-only などのエッジケースは agent の判断に委ねる。

## ステップ 2: ユーザー情報の収集

ステップ 1 のスキャン結果 + README / `CONTRIBUTING.md` / 既存 `CLAUDE.md` から全項目を推測してサマリ提示する。ユーザーは差分修正があれば該当項目だけ訂正する。推測不能な項目は "未定" として並べる。

```
[manage-context モード 2] 収集結果サマリ（推測）
  プロジェクト名: {リポジトリ名 or README から}
  概要: {README から / 取得不可なら "未定"}
  コア要件: {概要 + 主要機能から圧縮 / "未定"}
  クラウド: {IaC / CI 設定から / "未定"}
  LLM プロバイダ: {ステップ 1 の LLM SDK 検出から / 0 件なら "なし"}
  Web FW・言語: {ステップ 1 の技術スタックから}
  コーディング規約: {ステップ 1 のリンター・フォーマッターから}
  注意点: {README / CONTRIBUTING.md / 既存 CLAUDE.md から / なければ "なし"}
  未確定項目: {"未定" の一覧 or "なし"}

→ これで CLAUDE.md / docs/ を生成して良いですか？（"yes" / 修正したい項目）
```

修正希望があれば該当項目だけ訂正し、承認後にステップ 3 へ進む。

## ステップ 3: CLAUDE.md の生成

`.claude/skills/manage-context/templates/CLAUDE.md` をベースに、以下を埋めた CLAUDE.md を生成する：

| 埋める箇所 | 出典 |
|---|---|
| プロジェクト名 + 1-3 行サマリ | ステップ 2 質問 1・2 |
| **コア要件**（最優先要件 1 行） | ステップ 2 質問 3 |
| 注意点（任意） | ステップ 2 質問 7（あれば追記、なければテンプレのまま） |

生成した CLAUDE.md をユーザーに提示し、承認を得てからファイルに書き込む。

## ステップ 4: docs/ 配下のサブエージェント逐次生成

`docs/.steering/` と `docs/solutions/` はテンプレートからそのまま配置する：

```bash
mkdir -p docs/.steering docs/solutions
# .steering/.gitkeep と solutions/_index.md を配置
```

各ファイルは **サブエージェントを 1 ファイルにつき 1 つ、順次起動** して生成する。

### 起動順序

```
1. docs/product-requirements.md
2. docs/functional-design.md
3. docs/architecture.md
4. docs/agent-design.md
5. docs/repository-structure.md
6. docs/development-guidelines.md
7. docs/testing-guidelines.md
8. docs/glossary.md
```

### 各サブエージェントへの共通指示

- テンプレートファイル（`.claude/skills/manage-context/templates/docs/<ファイル名>`）のセクション構成に従うこと
- プレースホルダ（`{...}` 波括弧形式）と未確定 callout（`> **未確定**: ...`）を分析結果で置き換えること
- 分析結果が不十分なセクションは未確定 callout のまま残すこと
- 生成した内容を対象ファイルに直接書き込むこと
- **担当範囲外の情報は記載しない**（後述の境界に従う）
- **[`.claude/rules/docs-style.md`](../../../rules/docs-style.md) の書式統一ルールに準拠**（図記法は Mermaid 原則・内部リンクは `[file.md](file.md)` 形式・章番号は `## N. / ### N.M`・コードブロックは 15 行以内・TODO は引用 callout 形式）
- **[`.claude/rules/diagrams.md`](../../../rules/diagrams.md) の図記法ルールに従う**（システム構成図は Mermaid、ワイヤフレームとディレクトリツリーは ASCII）
- **特定スタック前提を埋め込まない**: ステップ 3 でユーザーが回答した実装スタック以外の固有名を生成しない
- **ユーザー回答にない技術判断は未確定 callout で残す**
- **テンプレ中の `{...}` プレースホルダ・「例: {...}」併記は、ユーザー回答に従って置換**
- **コード例の冒頭に `# 例（{言語/FW}）` コメントを付ける**
- **各サブエージェントには「ステップ 1 のリポスキャン結果」+「直前までに承認された前 doc 群の内容」の両方を入力として渡す**

### 各 doc 生成後の承認

各サブエージェントが書き込みを完了したら、ユーザーに：

```
docs/<ファイル名> を生成しました。内容を確認してください。
承認いただけたら次のサブエージェント（<次のファイル名>）に進みます。
```

承認後、次のサブエージェントを起動する。修正要望があれば反映してから次へ。

### 担当範囲の境界

各 doc の主な担当章は [`docs-content.md`](../../../rules/docs-content.md) の表（`記載する内容` 列）を一次ソースとする。

scan 固有の追加ルール:

- エージェント内部設計（プロンプト・ツール・メモリ・モデル設定）は **`agent-design.md` 担当が単独で扱う**。`architecture.md` / `functional-design.md` 担当は重複して扱わない
- `functional-design.md` の詳細はクロスリファレンスで `agent-design.md` / `architecture.md` に逃がす
- `glossary.md` の 7 区分（プロジェクト・利用者用語 / AI エージェント用語 / データ・ストレージ用語 / インフラ用語 / 開発・運用用語 / 認証・ロール用語 / ドメイン用語）のうち、プロジェクトで使わないカテゴリは行ごと削除

### 分析対象（実装側）の対応表

各 doc 担当サブエージェントがコード側で見るべき主な分析対象：

| 担当ファイル | 分析対象（実装側） |
|---|---|
| `product-requirements.md` | README / `CONTRIBUTING.md` / 既存 `CLAUDE.md` / ステップ 2 の収集サマリ |
| `architecture.md` | 依存ファイル / `.env.example` / IaC / 観測性ライブラリ / import 構造 |
| `repository-structure.md` | 実ディレクトリツリー / ファイルパターン / `docs/` 配下 |
| `functional-design.md` | ルーティング定義 / DB スキーマ / コンポーネント / SSE エンドポイント |
| `agent-design.md` | `prompts/` / `@tool` デコレータ / モデル指定 / メモリ実装 / ストリーミング定義 |
| `development-guidelines.md` | リンター設定 / 既存コードサンプリング / pre-commit |
| `testing-guidelines.md` | テストフレームワーク設定 / 既存テスト / 評価ディレクトリ |
| `glossary.md` | ドメインモデル型定義 / 頻出命名 / AI エージェント用語 |

詳細な分析手順は以下のサブセクションを参照。

### `product-requirements.md` 担当

担当: **何を作るか**（プロダクト概要・対象ユーザー・機能要件・受け入れ条件・非機能要件・スコープ外）。

分析対象:
- README → プロダクト概要・対象ユーザー・主要機能
- `CONTRIBUTING.md` / 既存 `CLAUDE.md` → 制約・運用方針
- ステップ 2 の収集サマリ（コア要件・概要・注意点）→ 冒頭セクション
- ルーティング定義・主要画面 → ユーザーストーリーの候補

検出できなかった項目（受け入れ条件・成功指標・スコープ外など）は未確定 callout のまま残す。

### `architecture.md` 担当

担当: **システムの配線とインフラ**。エージェント内部設計には踏み込まない。

分析対象:
- 依存関係ファイル（package.json, pyproject.toml 等）→ テクノロジースタック表
- ディレクトリ構成 → システム構成図（Mermaid or ASCII）
- LLM SDK / エージェントフレームワーク → LLM 基盤独立章に **どのプロバイダ SDK を使っているか** だけを記載
- 観測性ライブラリ → 観測性章
- `.env.example` → 環境変数表
- `.github/workflows/`, `terraform/`, `docker-compose.yml` 等 → ローカル開発環境章 / デプロイ章
- import 文・モジュール構成 → アーキテクチャパターン

### `repository-structure.md` 担当

分析対象:
- 実際のディレクトリツリー（depth 2-3）
- 各ディレクトリ内のファイルパターン → 配置ルール表
- フロントエンド・バックエンド・インフラの区分
- `docs/` 配下のファイル一覧 → ドキュメント章のツリー
- AI エージェント関連ディレクトリ（`prompts/`, `agents/`, `tools/`, `evaluations/`, `traces/` 等）の有無 → AI エージェント関連配置ルール

### `functional-design.md` 担当

担当: **ユーザー視点の仕様**（画面・API 概要・データモデル）。エージェント内部動作・システム配線詳細には踏み込まない。

分析対象:
- ルーティング定義 → 画面一覧・API エンドポイント一覧
- DB モデル / スキーマ定義 → データモデル全体図 + 各コンテナ役割表 + 主要スキーマ
- コンポーネントファイル → 画面構成・ワイヤフレーム
- SSE / WebSocket エンドポイント → ストリーミングを使う UI フローの概要のみ（契約詳細は `agent-design.md` 担当が記載）

### `agent-design.md` 担当

担当: **エージェント内部設計**。プロンプト・ツール・メモリ・モデル設定・ガードレール・拡張ポイントを集約する。

分析対象:
- プロンプトファイル（`prompts/` 配下、`*.txt`, `*.md`, ソース内のプロンプト文字列）→ システムプロンプトの構造・配置場所
- ツール定義（`@tool` デコレータ、`tools=[...]` 引数、function calling スキーマ定義）→ ツールカタログ表（name, input schema, 副作用, 認可要件）
- メモリ実装（会話履歴の保存箇所、要約処理、RAG 関連コード）→ メモリ・コンテキスト戦略
- モデル指定箇所 → タスク別モデル表
- LLM 呼び出し時のパラメータ → パラメータ表
- ストリーミングイベント定義 → ストリーミング契約表
- ガードレール実装 → ガードレールセクション
- 採用していない機能 → 拡張ポイント章

検出できなかった項目は TODO のまま残す。

### `development-guidelines.md` 担当

分析対象:
- リンター・フォーマッター設定ファイル → ツール・設定ファイル表
- 既存コード（5-10 ファイルをサンプリング）→ コーディングパターン
- プロンプト・ツールの編集に関する CI 設定や事前コミットフック → 「プロンプト・ツール開発規約」（エージェント不要案件は省略）
- Git 規約セクションは「`.claude/skills/workflow-conventions.md` を参照」のまま維持

### `testing-guidelines.md` 担当

分析対象:
- テストフレームワーク設定 → フレームワーク特定
- 既存テストファイル（3-5 ファイルをサンプリング）→ パターン抽出
- package.json / Makefile → テスト実行コマンド
- 評価関連ディレクトリ・評価ライブラリの有無 → 評価セクション（エージェント不要案件は省略）

### `glossary.md` 担当

分析対象:
- ドメインモデル（クラス / 型 / インターフェース定義）を検索
- 頻出するドメイン固有の命名を抽出
- 日本語・英語・コード命名の対応表を生成
- AI エージェント用語（Conversation, Tool Call, Trace, Eval, Guardrail, Context Window 等）はデフォルトで含める（エージェント不要案件は章ごと削除）

## ステップ 5: 完了報告

生成・配置したファイルの一覧を報告する。

**書式準拠の確認を促す**：

- 生成された CLAUDE.md と docs/ が [`.claude/rules/docs-style.md`](../../../rules/docs-style.md) のルールに準拠していることを確認してください
- 不一致がある場合は手動で修正してください（特に `docs-style.md §9` のコードブロック 15 行ルール）

次のステップを提案する：

- 各 docs ファイルのプレースホルダ（`{...}`）と未確定 callout を埋める

## 注意事項

- CLAUDE.md の「重要な原則」セクションはテンプレートの内容をそのまま使う（変更しない）
- サブエージェントの分析結果が不十分なセクションは TODO のまま残す
- 各 docs ファイルは必ずユーザー承認を挟んでから次のサブエージェントを起動する
- `.claude/agents/`, `.claude/rules/`, `.claude/skills/`（manage-context 以外）は本フローで配布しない
- `.claude/skills/workflow-config.md` も触らない（責務外）
