# 目的別プレイブック

各スキル（create-pr, fix-review 等）が参照する作業フローと振り返り規約。

## 解決記録の振り返り

`/create-pr` と `/fix-review` の手順内で実行する。

本作業中に **記録すべき知見が発生していないか必ず立ち止まって振り返る**。Claude が独断で「記録不要」と判断してはならない。スキップする場合は理由を明示する。

### 振り返り対象の例

- 公式ドキュメントに反するパターンや見落としやすい制約に遭遇した
- 複数の選択肢から選んだ際の根拠（non-trivial な技術判断）
- 後続案件でも再遭遇しそうな問題と回避策
- ハマって時間を使った解決策

### 手順

1. 直近のコミット・差分・会話を再確認し、**記録価値のある知見の候補を列挙する**
2. 候補がある場合: ユーザーに「以下の知見について `/record-solution` を実行しますか？」と提案する
3. 候補がない場合: **「PR 本文や対応コメントに書いたから不要」と独断しない**。「振り返った結果、再利用価値のある知見はなさそうです（理由: ◯◯）」とユーザーに明示し、承認を得てから次へ進む

## 目的別プレイブック

すべてのプレイブックは下記の標準フローを踏襲する。各プレイブックは作業の性質に応じて特有の注意点・スキップ可能な工程を明示する。

```
/create-issue → ブランチ作成 → 実装 → コミット → /create-pr → /review-pr → /fix-review → GUI 上でマージ
```

### feat — 新機能追加

新しい機能・コンポーネント・API エンドポイント等を追加する場合。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）
2. `/create-branch` — `feat/<番号>-<簡潔な説明>`
3. `/create-steering` — 設計判断ありなら通常（requirements.md + design.md + tasks.md）／ なければ軽量（index.md）
4. 必要なら `tech-researcher` エージェントで技術選定の最新化（**API リファレンスや使い方が不確かな時もここで確認** — training data の古さ・幻覚を回避）
5. 実装 → 実装中に API シグネチャ・使い方が不確かな箇所が出たら `tech-researcher` で公式 docs を確認 → コミット（pre-commit が自動実行）
6. **実装単位ごとに `test-engineer` サブエージェントを呼び出し、テスト実行・カバレッジ確認・lint チェックを行う**。失敗時は提案された修正内容を確認し parent 側で適用する（subagent 隔離による context 汚染防止）
7. `/create-pr`
8. **別セッションで** `/review-pr <PR番号>`（第三者視点）
9. `/fix-review <PR番号>`（指摘対応）
10. GUI 上でマージ

**スキップ可**: 自明な機能（定数追加、軽微な UI 調整等）なら steering は軽量で OK。

**PR 本文に推奨のセクション**: 修正内容の概要図 / ファイル別の修正詳細 / エビデンス（UI 変更がある場合）/ 運用ドキュメント（環境変数追加がある場合）

### fix — バグ修正

バグレポート・リグレッション・既知不具合の修正。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）— **再現手順を含める**
2. `/create-branch` — `fix/<番号>-<簡潔な説明>`
3. `/create-steering` — 通常は軽量（設計判断なし）／ 大規模な修正なら通常
4. **失敗するテストを先に書く**（バグを再現させる）— `test-engineer` でテストが「期待どおり失敗する」ことを確認
5. 修正実装
6. **`test-engineer` サブエージェントでテスト実行・カバレッジ確認・lint チェック**。テストが通ることと、既存テストへのリグレッションが無いことを確認
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: typo / コメント修正 など自明な変更は Issue 不要、軽量 steering もスキップ可。

**PR 本文に推奨のセクション**: 再現手順 / 修正前後の挙動（エビデンスとしてログやスクショ）/ 再発防止策（テスト追加内容）

### chore — 設定・雑務

ディレクトリ構造、依存追加、CI 設定、ツール設定変更等。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）
2. `/create-branch` — `chore/<番号>-<簡潔な説明>`
3. `/create-steering` — **複数の選択肢から選ぶ場合は必ず通常**（後で経緯を追跡可能にする）
4. `tech-researcher` で最新版・ベストプラクティス・公式 docs（API リファレンスを含む）を確認
5. 設定ファイル作成・更新（実装中に詳細仕様が不確かなら追加で `tech-researcher` を呼ぶ）
6. 実機動作確認（実行コマンドを tasks.md に記録）
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: lock ファイル更新のみ等の決まり切った設定なら steering は軽量。

**注意点**:

- pre-commit / CI 設定変更は **`pre-commit run --all-files` で全体検証**
- ツール選定は **`tech-researcher` で再評価**してから決定（半年〜1 年で陳腐化する）

**PR 本文に推奨のセクション**: 影響範囲（どのスキル・ツールが影響するか）/ 動作確認手順 / 運用ドキュメント（環境変数・設定変更がある場合）

### docs — ドキュメント変更

README、設計図、用語集、運用手順等の追加・更新。

**手順**:

1. （任意）`/create-issue` — 大規模な変更なら作る
2. `/create-branch` — `docs/<簡潔な説明>`（Issue なしなら番号も省略）
3. `/create-steering` — 通常スキップ。新規ドキュメント追加なら軽量
4. 編集
5. `/create-pr`
6. 別セッションで `/review-pr <PR番号>`
7. `/fix-review <PR番号>`
8. GUI 上でマージ

**スキップ可**: typo / リンク修正は Issue 不要、直接ブランチで OK。

**注意点**:

- **新規ドキュメント作成前に `.claude/rules/docs-content.md` の役割表を確認** — 既存 8 ファイルのいずれかに統合できないか検討

**PR 本文に推奨のセクション**: 該当ドキュメントへのリンク / 変更前後の対応関係（移動・分割した場合）

### refactor — リファクタリング

機能変更を伴わない構造改善・命名変更・モジュール分割等。

**手順**:

1. `/create-issue` — 範囲・狙いを明示
2. `/create-branch` — `refactor/<番号>-<簡潔な説明>`
3. `/create-steering` — **必ず通常**（設計判断ある）
4. **着手前に既存テストが通ることを確認**（ベースライン）— `test-engineer` でベースラインを取る
5. リファクタ実施
6. **`test-engineer` サブエージェントで既存テストが全部通ることを再確認**（機能変更なしの担保）。lint クリーンも合わせて確認
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: 1 ファイル内の単純な命名変更程度なら steering 軽量も可。

**PR 本文に推奨のセクション**: 修正内容の概要図（変更前後のアーキテクチャ）/ ファイル別の修正詳細 / テスト網羅性（既存テストが通ったことのエビデンス）
