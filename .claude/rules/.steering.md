# 作業計画ドキュメント

## ディレクトリ命名規則

```
docs/.steering/[YYYYMMDD]-[開発タイトル]/
```

**例：**
- `docs/.steering/20250103-initial-implementation/`
- `docs/.steering/20250115-add-tag-feature/`
- `docs/.steering/20250120-fix-filter-bug/`

## ファイル構成

設計判断の有無によってフォーマットを使い分ける。

### 形式の判定基準

以下のいずれかに該当すれば **通常 steering**、いずれにも該当しなければ **軽量 steering**。迷う時は通常を選ぶ（後から削るほうが、後から書き足すより楽）。

- 実装方法に 2 つ以上の選択肢がある
- 既存コードに同じパターンがない
- 複数ファイル・コンポーネントに影響する

### 軽量（設計判断なし）

`index.md` 1ファイルに「何を・なぜ・どう」を3行で記録する。書いたら作業開始してよい。

```markdown
# [作業タイトル]

## 何を
（変更・追加する内容を 1 行）

## なぜ
（理由を 1〜2 行）

## どう
（実装アプローチを 1 行）
```

### 通常（設計判断あり）

各ディレクトリに以下の3ファイルを作成する。

#### requirements.md — 何をやるか
- 変更・追加する機能の説明
- ユーザーストーリー
- 受け入れ条件
- 制約事項

#### design.md — どう作るか
- 実装アプローチ
- 変更するコンポーネント
- データ構造の変更
- 採用する変更内容の選定理由（**採用しなかった選択肢とその却下理由を必ず書く**）
- 影響範囲の分析
- データフロー・処理パイプライン・複数コンポーネントの依存関係など、言語化しづらい構造があれば図（Mermaid 推奨）を埋め込むことを推奨（必須ではない。軽量 steering や小さい判断では過剰になるので不要）。記法は [diagrams.md](diagrams.md) 参照

#### tasks.md — 具体的な手順
- 具体的な実装タスク
- タスクの進捗状況（チェックボックス形式）
- 完了条件
- タスク間の依存関係を明示し、並列実行可能なタスクと実行順序を記載する

## タスクの記述・更新ルール

### スキップ時の表記

技術的理由でタスクが不要になった場合のみスキップ可能（「時間の都合」「複雑だから後回し」は禁止）。表記:

```markdown
- [x] ~~タスク名~~（不採用理由: 具体的な技術的理由）
```

### 実装後の振り返り

実装完了時、`tasks.md` の末尾「実装後の振り返り」セクションを更新する:

- 実装完了日
- 計画と実績の差分（方針変更・追加タスク・スキップしたタスクとその理由）
- 学んだこと
- 次回への改善提案
