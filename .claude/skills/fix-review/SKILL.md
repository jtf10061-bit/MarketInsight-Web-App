# レビュー指摘対応スキル

PR に付いたレビューコメントを取得し、各指摘への対応方針をユーザーと確認した上でコード修正を実施する。

**重要**: まず以下 4 ファイルをすべて読み込むこと。
- `.claude/skills/workflow-config.md`（共通設定）
- `.claude/skills/workflow-conventions.md`（コミットメッセージ規約）
- `.claude/skills/workflow-issues.md`（完了条件の更新手順）
- `.claude/skills/workflow-playbooks.md`（解決記録の振り返り）

## 引数の解析

- PR 番号（数値）: 未指定の場合は現在のブランチに紐づく PR を自動検出する

## 現在の状態

- 現在のブランチ: !`git branch --show-current`
- Git ステータス: !`git status --short`

## ワークフロー

### ステップ 1: PR の特定

1. `$ARGUMENTS` に PR 番号が指定されている場合はそれを使用する
2. 未指定の場合:
   ```bash
   gh pr view --json number --jq '.number'
   ```
3. PR が見つからない場合はエラーを報告して停止する

### ステップ 2: PR 情報の取得と表示

```bash
gh pr view <PR番号> --json number,title,state,headRefName,baseRefName,url
```

PR が `open` でない場合は警告し、続行するか確認する。

### ステップ 3: 作業ブランチの確認

1. 現在のブランチが PR の `headRefName` と一致することを確認する
2. 一致しない場合はチェックアウトするか確認する
3. 未コミットの変更がある場合は警告する

### ステップ 4: レビューコメントの取得と一覧表示

2種類のレビュー情報を取得する:

1. **PR レビュー（全体コメント）**:
   ```bash
   gh pr view <PR番号> --json reviews
   ```
2. **インラインコメント（コード行への指摘）**:
   ```bash
   gh api repos/{owner}/{repo}/pulls/<PR番号>/comments
   ```

一覧形式で表示する:
```
=== レビュー指摘一覧 ===

[1] @レビュアー名 - ファイル: src/auth/login.ts (L42)
    「この入力バリデーションが不足しています」

[2] @レビュアー名 - ファイル: src/api/handler.ts (L15-L20)
    「エラーハンドリングを追加してください」

合計: N 件の指摘
```

指摘が 0 件の場合はその旨を報告して終了する。

### ステップ 5: 各指摘への対応方針の確認

各指摘について、ユーザーに対応方針を確認する:
1. 修正する
2. スキップする（対応不要）
3. 後回しにする

全ての指摘について方針を確認した後、対応サマリーを表示する。

### ステップ 6: コード修正の実施

「修正する」と決定した各指摘について順番に修正する:
1. 対象ファイルを読み込み、指摘箇所を確認する
2. コードを修正する
3. 修正内容をユーザーに提示し、確認を得る

### ステップ 7: コミットとプッシュ

1. コミットメッセージを生成する（修正した指摘の概要を含める）
2. コミットメッセージをユーザーに提示し、承認を得る
3. ステージングとコミットを実行する:
   ```bash
   git add <修正したファイル一覧>
   git commit -m "<メッセージ>"
   ```
   - `.env` や認証情報ファイルは絶対にステージングしない
   - `git add -A` や `git add .` は使わず、ファイルを明示的に指定する
4. リモートにプッシュする:
   ```bash
   git push origin <現在のブランチ>
   ```

### ステップ 8: 関連 Issue の完了条件を再確認

PR が「Closes #N」で参照する Issue について、レビュー対応で達成状況が変わったか確認する。変化があれば `workflow-issues.md` の **「完了条件の更新手順」** に従って更新する。

変化がなければスキップして次のステップへ。

### ステップ 9: PR への対応サマリーコメント投稿

レビュアーが対応状況を把握できるよう、PR にコメントを投稿する:

```markdown
## レビュー指摘への対応

コミット: <ハッシュ>

### 対応済み

| # | 指摘 | 対応内容 |
|---|------|---------|
| 1 | 指摘の要約 | 具体的な対応内容 |

### スキップ

| # | 指摘 | 理由 |
|---|------|------|
| N | 指摘の要約 | スキップした理由 |
```

コメント内容をユーザーに提示し、承認を得てから投稿する。

### ステップ 10: 解決記録の振り返り

[`workflow-playbooks.md`](../workflow-playbooks.md) の **「解決記録の振り返り」** セクションに従って実行する。

### ステップ 11: 完了報告

- PR 番号・タイトル（URL）
- 対応した指摘: N 件
- スキップした指摘: N 件
- 後回しにした指摘: N 件
- コミットハッシュ・変更ファイル一覧
- 更新した Issue（該当する場合）

後回しにした指摘がある場合はリマインドする。

## 注意事項

- `outdated` のコメントは対応要否をユーザーに確認する
- フォースプッシュは絶対に行わない
- `.env` や認証情報ファイルは絶対にステージングしない
- 修正中にセキュリティ上の懸念を発見した場合は即座に報告する
- 修正に伴って docs / CLAUDE.md（役割対応表は [`.claude/rules/docs-content.md`](../../rules/docs-content.md) を参照）に齟齬が生じる場合は同じコミットで更新する
- approve / merge は人間が GitHub Web UI から行う運用とする
