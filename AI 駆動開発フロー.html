2.4
Pre-commit 自動チェック

AI がコミットを試みた瞬間に走る機械チェック。一つでも失敗すればコミット拒否 → AI が修正 → 通るまで成立しません。

言語別 lint + format
言語依存・要差し替え
Ruff（Python）／ Biome（TypeScript / JavaScript）
※ 導入先の言語に応じて差し替え
シークレット検出
言語非依存
gitleaks：API キー・トークン等の誤コミットを検出
共通衛生フック
言語非依存
末尾空白・改行コード・コンフリクト記号など、ファイルの基本整形を機械チェック
設計の意図
Skills が「手順」を自動化するのに対し、pre-commit は「成果物」を機械的にチェックします。開発者レビューが届く前段階で機械的に弾けるものは弾いておくことで、レビュー対象を「業務仕様として妥当か」という本質論点に集約できます。
2.5
GitHub Actions

テスト実行・@claude メンション・自動レビューで、ローカルと GitHub の二段構えで運用します。

予定
テスト実行

PR / push 時に自動テスト + カバレッジを実行。実装中の test-engineer（ローカル）と独立して、リモート側でも網羅チェック。

運用中
対話的な作業依頼

Issue / PR コメントで @claude メンション → 応答・実装・PR 作成。ローカル Claude Code を立ち上げずに GitHub 上から直接起動。

運用中
PR 自動レビュー

PR オープン時に Claude が自動でコードレビュー（review-pr スキルの観点）。開発者レビューが届く前に第一次フィードバックが付く。

※ GitHub Actions 上での AI 実行は、ローカルの Claude Code と比較して実行精度が落ちる傾向があります。比較的簡単な作業や定型的な処理でのご利用をおすすめします。

具体例

/fix-review がレビュー指摘を実装に反映。最終的に開発者が業務仕様として妥当か判断し、Approve する。このステップだけが開発者判断（Approve）を含む。

具体例
  • AI が指摘内容を修正（追加テスト・通知処理）
  • レビューで docs の不整合が指摘された場合、AI が一緒に修正
  • 開発者が「業務仕様として妥当か」「変更範囲が過大でないか」を確認
  • 問題なければ Approve

具体例

04Playbooks
Chapter Four

プレイブック 5 種

標準フローは 1 本ですが、作業の性質に応じて 5 つのプレイブックが用意されており、steering の作り込みやサブエージェントの呼び出し方が変わります。

4.1

5 プレイブック比較マトリクス

feat fix chore docs refactor
用途 新機能追加 バグ修正 設定・雑務 ドキュメント 構造改善
Issue 必須 必須 必須 任意 必須
ブランチ feat/... fix/... chore/... docs/... refactor/...
steering 通常／軽量 軽量 必ず通常 スキップ 必ず通常
サブエージェント tech-researcher
test-engineer		 test-engineer tech-researcher — test-engineer
PR 本文推奨 概要図 / 詳細 /
UI エビデンス		 再現手順 / 前後 /
再発防止策		 影響範囲 /
動作確認 / 運用		 該当リンク /
変更前後対応		 アーキ図 /
詳細 / 網羅性

※ 通常 = requirements.md + design.md + tasks.md（3 ファイル）／ 軽量 = index.md（1 ファイル）

使い分けの考え方
設計判断が必要かどうかで steering の重さを切り替えます。feat と refactor は意思決定の塊なので必ず通常 steering、fix や docs は軽量で十分。chore は「複数の選択肢から選ぶ場合は必ず通常」とすることで、後で経緯を追跡できるようにします。

Chapter Five

記録の設計

Issue / .steering / PR / docs の 4 つに関して、それぞれが何で、どのスキルで作るかをご紹介します。

5.1

Issue

記載する内容
  • 受け入れ条件
  • 関連リンク（親 Issue / Epic 等）
  • 進行中の会話・確認・進捗報告
作成方法

Claude Code 上で /create-issue を実行し、会話からテンプレートを元に作成。GitHub Sub-issues API で親子関係も自動設定されます。

5.2

.steering

記載する内容

1 作業 = 1 ディレクトリで判断履歴を残します。

  • 要件（何をするか / なぜするか）
  • 設計の意思決定（採用案・代替案・却下理由）
  • 作業進捗・動作確認結果
作成方法

Claude Code 上で /create-steering を実行し、YYYYMMDD-タイトル/ ディレクトリと 3 ファイル雛形を AI が生成します。

requirements.md何をするか / なぜするか / 想定読者 / 成果物 / 範囲
design.mdどうアプローチするか / 代替案 / 採用理由 / 制約 / リスク
tasks.md作業計画 / 進捗 / 動作確認結果

設計判断のない軽量作業では index.md 1 ファイルで済ませる運用も用意。

5.3

PR

記載する内容

差分・テスト結果・関連リンクが集約される、レビューの中心。

  • コード差分 / ドキュメント差分
  • テスト結果サマリ
  • Issue・steering へのリンク
  • 修正サイクルの履歴（修正後コメント）
作成方法

初回: Claude Code 上で /create-pr を実行し、構造化テンプレートで PR 本文を生成。

修正後: /fix-review でレビュー指摘の対応内容と再テスト結果を PR コメントとして追記。

※ 修正後コメントへの再テスト結果追記は 運用ルールとして想定している段階（/fix-review スキル定義への組み込みは未実装）。

5.4

docs

記載する内容

恒久参照する現在仕様。詳細設計もここに集約。

  • 要件定義
  • 機能設計（画面・API・データモデル）
  • アーキテクチャ
  • 規約（コーディング・テスト方針）
  • 用語集
更新方法

実装やレビュー対応の中で、関連する docs を AI が一緒に更新します。役割は .claude/rules/docs-content.md で定義されているため、内容に応じて適切なファイルが選ばれます。

product-requirements.mdプロダクト要件定義
functional-design.md機能設計（画面・API・データモデル）
architecture.md技術仕様（システム構成・スタック・観測性）
repository-structure.mdディレクトリ構成リファレンス
development-guidelines.mdコーディング規約・命名・環境変数管理
testing-guidelines.mdテスト方針・カバレッジ基準
glossary.md用語集

hotfix ガイド — Emergency Flow

緊急対応（hotfix）の
全体フロー

本番障害レベルの事象を最短で復旧し、事後整理は通常フローに戻す

通常フロー（feat / fix / refactor）は develop 起点ですが、hotfix のみ main 起点の例外フローです。復旧を最優先にし、Issue・steering の作成や develop への反映は GitHub Actions が肩代わりします。本ガイドでは、ブランチ作成から事後整理までの一連を画面イメージとあわせて示します。

hotfix にすべきか — 判断マトリクス

「急ぎ」と「緊急対応」は分けて運用します。下表のいずれかに該当する事象のみ hotfix を使い、それ以外は通常の /create-branch に回します。AI に緊急判断はさせず、開発者がスキル起動時の再確認に明示的に 「はい（緊急対応）」 と答えた場合のみ進行します。

事象 分類
本番業務が止まっている hotfix
本番データ・帳票・CSV・メール送信・外部連携などに重大な誤り hotfix
次回通常リリースまで待つと業務影響・混乱が大きい hotfix
セキュリティ上、即時に塞ぐ必要がある hotfix
依頼者が急いでいる／納期が近い／小さい修正だからすぐ出したい 通常 /create-branch
通常フローで Issue を作成する余裕がある 通常 /create-branch

全体フロー

開発者が手で行うのは ブランチ作成・最小修正コミット・PR 作成 の 3 点だけ。緊急対応 Issue の作成、develop への反映、release ブランチへの伝播は Action が自動で行い、Issue クローズは事後整理 PR の Closes #N で GitHub 標準機能が処理します。

Step 1

ブランチ作成

/create-hotfix-branch main 起点

通常の /create-branch と異なり、main 起点で hotfix/* ブランチを切る専用スキル。Issue や steering の作成より前に着手してよい例外フローです。

緊急判断は人間が行う
スキルは起動直後に「本番障害レベルですか？通常の急ぎ修正であれば /create-branch を使ってください」と再確認します。「はい」と明示的に答えた場合のみ次に進み、それ以外は中断します。
前提状態
  • 本番障害レベルの事象が発生している（人間が判断済み）
  • 未コミットの変更がない（あれば stash / コミット）
  • main がリモートと同期できる状態

PR 作成 → main マージ

/create-pr hotfix モード

current branch が hotfix/* の場合、/create-pr は自動で hotfix モードに入り、専用の PR 本文テンプレートを使います。復旧優先・最小修正の原則を反映した簡潔な構成です。

hotfix PR 本文テンプレート
## 障害概要 [必須] <一行で発生事象を要約> ## 関連 Issue [必須] <Closes #番号（あれば） / 「マージ後 Action が緊急対応 Issue を自動作成」（なければ）> ## 修正内容 [必須] <復旧に必要な最小修正のみ。リファクタや関連改善は含めない> ## 復旧確認方法 [必須] <本番反映後の確認手順 / 監視項目 / 期待される挙動> ## 事後整理の予定 [必須] - [ ] 恒久対応案の検討 - [ ] ナレッジ化 - [ ] 再発防止策の登録
運用ポイント
  • ベースブランチは main（develop ではない）
  • 人間レビュー必須（Auto-merge は使わない）
  • マージ後は本番反映 → 復旧確認まで人間が責任を持つ
  • 軽微事象で事後整理が不要なら「事後整理不要（原因・再発防止判断は Issue コメントで完結）」と記載

Step 4

事後整理

通常フローに復帰 develop 起点

復旧が終わったら、緊急対応 Issue を起点に 通常フロー（develop 起点） に戻ります。恒久対応・ナレッジ化・再発防止策の登録を、平時の feat/fix/refactor プレフィックスで行います。

緊急対応 Issue の構造
## 対応経緯 関連 hotfix PR: #<番号> （事後整理で記録） ## 恒久対応案 （事後整理で記録） ## 完了条件 - [ ] 事後整理 PR を develop へマージ（本 Issue を `Closes #N` で参照） - [ ] 軽微事象の場合はコメントで原因と再発防止判断を残してそのままクローズ
事後整理 PR の例
  • ブランチ: fix/<Issue番号>-csv-encoding-postmortem など通常プレフィックス
  • ベース: develop（通常フロー）
  • 本文に Closes #<緊急対応 Issue 番号> を含めれば、develop（デフォルトブランチ）マージ時に GitHub 標準機能が Issue を自動クローズ
軽微事象の場合
  • 事後整理 PR を出さずに、Issue コメントで原因と再発防止判断を残してクローズしてよい
  • 「全件で恒久対応 PR を強制」しないことで、Action による Issue 自動作成のコストが過大にならないようにする

Step 5

事前準備（運用開始前に 1 度だけ）

Settings workflow 配置

hotfix フローを動作させるために、リポジトリ側で 1 度だけ 行う設定があります。これを満たしていないと Action 連鎖が途中で止まります。

1. Workflow permissions（Actions が PR を作成できる権限）

[develop 反映] PR / [release 反映] PR を Action が自動作成するため、リポジトリ設定で 「Allow GitHub Actions to create and approve pull requests」 を ON にする必要があります。

設定場所
  • Settings → Actions → General → Workflow permissions
  • Allow GitHub Actions to create and approve pull requests にチェックを入れて保存
未設定時の挙動
Action のログに GitHub Actions is not permitted to create or approve pull requests エラーが出て、PR 作成が失敗します。
2. ワークフロー yaml の配置先（main / develop 両方）

GitHub Actions は PR のベースブランチに存在する yaml しか発火しません。hotfix フローは main / develop の両方をベースに発火するため、両ブランチに workflow を取り込んだ状態にしておきます。

ワークフロー ベースブランチ 取り込み先
hotfix-create-issue.yml main main に配置
hotfix-backport-to-develop.yml main main に配置
hotfix-propagate-to-release.yml develop develop に配置

運用上は main / develop の両方に同じ yaml セットを置くのが最も安全です。ベースブランチごとに分けるとメンテで取りこぼしやすく、片方にだけ存在する状態を作るとフローが途中で止まります。

3. デフォルトブランチ

本フローは デフォルトブランチ = develop を前提にしています。事後整理 PR が develop（デフォルト）にマージされる時、GitHub 標準機能の Closes #N 自動クローズが緊急対応 Issue を閉じます。

設定場所
  • Settings → Branches → Default branch を develop に設定

main をデフォルトのまま運用すると、develop マージで Closes #N が発火せず Issue が閉じません。その場合は補完用 Action（hotfix-close-issue.yml）が別途必要になります。

# Issue 作成スキル

GitHub Issue を作成する。大きなタスクの場合は子 Issue に分割して作成する。

**重要**: まず `.claude/skills/workflow-config.md` と `.claude/skills/workflow-issues.md` を読み込み、共通設定および Issue 規約を取得すること。

## 引数の解析

`$ARGUMENTS` からオプションを取得する。

- タイトルまたは説明テキスト（必須）
- `--parent <Issue番号>`: 親 Issue の番号（子 Issue として作成する場合）

## 現在の状態

- 現在のブランチ: !`git branch --show-current`
- 既存の .steering: !`ls docs/.steering/ 2>/dev/null || echo "なし"`

## ワークフロー

### ステップ 1: 情報収集

1. `$ARGUMENTS` からタイトルとオプションを解析する
   - タイトルが未指定の場合はユーザーに入力を求める
2. 既存の Issue と重複がないか確認する:
   ```bash
   gh issue list --state open --json number,title --limit 50
   ```
   - 類似タイトルの Issue が見つかった場合は警告し、続行するか確認する
3. `--parent` が指定されている場合、親 Issue の存在を確認する
4. `docs/.steering/` 配下に関連する steering があれば参照する

### ステップ 2: Issue 本文の生成

[`references/issue_template.md`](references/issue_template.md) のテンプレートに従って本文を生成する。各セクションはステップ 1 で集めた情報をもとに埋める。

### ステップ 3: 規模評価と分割提案

`workflow-issues.md` の **「子 Issue の運用」** に記載された分割条件に該当する場合、子 Issue への分割を提案する。

分割する場合:
- 推奨する分割案（3〜7 件の子 Issue タイトル）を提示する
- ユーザーの承認を得てから分割モードで作成する

### ステップ 4: ラベル決定

ラベル軸の定義と付与フローは `workflow-issues.md` の **「ラベル体系」** および **「ラベル付与の運用フロー」** を参照する。本ステップで必要な自動化コマンド：

#### 親 Issue（Epic）作成時

`epic` ラベル + `area:` ラベルを 1〜複数付ける（`parent:` は付けない）。新規 Epic の場合は `parent:<新番号>-<短縮名>` ラベルを発行する旨をユーザーに通知。

#### 子 Issue 作成時

`--parent <番号>` 指定時、親 Issue から `area:` と `parent:` ラベルを取得して初期候補とする：

```bash
# 親の area: ラベル一覧を取得（子の初期候補にする）
gh issue view <親番号> --json labels --jq '[.labels[] | select(.name | startswith("area:")) | .name] | join(",")'

# 親に紐付く parent: ラベル名を取得（子に付与する）
gh label list --search "parent:<親番号>-" --json name --jq '.[0].name'
```

ユーザーに「子の作業範囲は親と同じか／異なる／追加領域か」を確認し、最終的な `area:` を決定する。`priority:` は任意（必要なら確認）。

### ステップ 5: ユーザー確認

以下を一覧表示し、ユーザーの承認を得る:
- タイトル
- 本文
- 親 Issue（該当時）
- 付与予定ラベル（`epic` / `area:` / `parent:` / `priority:`）
- 子 Issue 計画（分割時）

### ステップ 6: Issue 作成

```bash
gh issue create --title "タイトル" --body "本文" --label "area:agent,parent:27-claude-tooling"
```

子 Issue として作成する場合は親子関係を設定する。コマンドは `workflow-issues.md` の **「Sub-issues API の使い方」** を参照。

分割モードの場合：
1. 親 Epic を先に作成（`epic` + `area:` を付与、`parent:` は付けない）
2. 親用に `parent:<新番号>-<短縮名>` ラベルを発行（`gh label create`）
3. 各子 Issue を順番に作成・紐付け（`area:` + `parent:<新番号>-<短縮名>` を付与）

### ステップ 7: 完了報告

- 作成した Issue の番号・タイトル・URL
- 親子関係（該当する場合）

## 注意事項

- Issue 本文にセキュリティ上の機密情報を含めない
- 親 Issue の本文を更新する際は既存の内容を保持する
- 子 Issue 作成中にエラーが発生しても、作成済みの Issue は削除しない

# ブランチ作成スキル

Issue を選択し、規約に沿った命名で作業用ブランチを作成する。

**重要**: まず `.claude/skills/workflow-config.md` と `.claude/skills/workflow-conventions.md` を読み込み、ブランチ戦略および命名プレフィックス（Type 規約）を取得すること。

## 引数の解析

`$ARGUMENTS` からオプションを取得する。

- `--issue <番号>`: 関連する Issue 番号（指定時は Issue 選択をスキップ）
- 説明テキスト: ブランチ名のヒントとして使用

## 現在の状態

- 現在のブランチ: !`git branch --show-current`
- Git ステータス: !`git status --short`

## ワークフロー

### ステップ 1: 事前チェック

1. 未コミットの変更がないことを確認する
   - ある場合はユーザーに警告し、stash するか先にコミットするか確認する
2. リモートの最新を取得する:
   ```bash
   git fetch origin
   ```

### ステップ 2: Issue の選択

`--issue` が指定されている場合はこのステップをスキップする。

1. オープンな Issue 一覧を表示する:
   ```bash
   gh issue list --state open --json number,title --limit 20
   ```
2. 一覧をユーザーに提示し、どの Issue に着手するか確認する
3. Issue が不要な場合（Issue なしで作業する場合）はその旨を確認してステップ 3 に進む

### ステップ 3: ブランチ名の決定

1. Issue のタイトルと説明から適切なプレフィックスを判定する（`workflow-conventions.md` の Type 規約表に従う）
2. ブランチ名を生成する:
   - Issue ありの場合: `<プレフィックス>/<Issue番号>-<説明>`（例: `feat/9-nextjs-project-init`）
   - Issue なしの場合: `<プレフィックス>/<説明>`（例: `docs/update-readme`）
3. 命名ルール:
   - 英小文字・ハイフン区切り
   - 簡潔で内容が分かる名前
4. ユーザーに提示して承認を得る:
   - **ブランチ名**: `feat/123-add-search-filter`
   - **ベースブランチ**: `workflow-config.md` のデフォルトベースブランチ
   - **関連 Issue**: #123

### ステップ 4: ブランチ作成

```bash
git switch -c <ブランチ名>
```

### ステップ 5: 完了報告

作成したブランチ名とベースブランチを報告する。

Issue が紐づいている場合は、Issue の完了条件（チェックボックス）があれば表示する:
```bash
gh issue view <Issue番号> --json body
```

## 注意事項

- 同名のブランチが既に存在する場合はエラーを報告して停止する
- ベースブランチは `workflow-config.md` のデフォルトベースブランチを使用する

# create-steering

作業着手前に **必ず** steering を作るのが本テンプレートの運用ルール。このスキルはその作成を対話的にガイドする。

形式・命名規則・各ファイルに書く項目は [`.claude/rules/.steering.md`](../../rules/.steering.md) を参照すること。このスキルは **作成のワークフロー** を担当する。

---

## 動作原則

1. **1 ファイルごとにユーザー承認を得てから次へ進む**（特に通常 steering の場合）
2. **形式判定で迷ったら通常 steering を選ぶ**（判定基準は `.steering.md` 参照）
3. **タイトルは英数字ハイフン区切り**（例: `add-search-filter`、`fix-auth-bug`）。日本語は避ける（パス操作時のトラブル回避）
4. **承認なく次のファイルに進まない**

---

## ワークフロー

### Step 1: 作業内容のヒアリング

以下を確認する：

- 何をする作業か（1〜3 行で）
- 既存のドキュメントへの影響（永続的 docs の更新が必要か）
- 設計判断の有無

### Step 2: 形式判定

`.steering.md` の判定基準に従って軽量／通常を決める。

### Step 3: ディレクトリ作成

```bash
mkdir -p docs/.steering/[YYYYMMDD]-[英数字ハイフン区切りタイトル]
```

- `YYYYMMDD` は今日の日付（システムから取得）
- 既に同名ディレクトリが存在する場合はユーザーに確認

### Step 4a: 軽量 steering の作成

`.steering.md` の軽量フォーマットに従って `index.md` を作成。書いたら作業開始してよい。承認は最終確認のみ。

### Step 4b: 通常 steering の作成

[`templates/`](templates/) 配下の雛形を起点に、3 ファイルを **1 ファイルずつ** ユーザー承認を取りながら作成する。各ファイルのプレースホルダ `{...}` を作業内容で埋めていく。

1. [`templates/requirements.md`](templates/requirements.md) → `docs/.steering/[ディレクトリ]/requirements.md` を作成 → ユーザー確認 → 承認後に次へ
2. [`templates/design.md`](templates/design.md) → `docs/.steering/[ディレクトリ]/design.md` を作成。複数選択肢を検討し却下理由を必ず書く → ユーザー確認 → 承認後に次へ
3. [`templates/tasks.md`](templates/tasks.md) → `docs/.steering/[ディレクトリ]/tasks.md` を作成 → ユーザー確認 → 承認後に作業開始可能

### Step 5: 完了報告

作成したファイル一覧と次のアクションを報告。

---

## 永続的ドキュメントへの影響判定

ステアリング作成時に確認する：

- 変更が `docs/product-requirements.md` `architecture.md` `glossary.md` の内容に影響するか
- 影響する場合は、別途 docs 側の更新が必要 → tasks.md の最後にタスクとして追加
- 環境変数の追加 → `.env.example` 更新タスクを必ず tasks.md に含める（[`restricted-files.md`](../../rules/restricted-files.md)）

---

## エッジケース

| ケース | 対応 |
|------|------|
| 同日に複数の作業を開始 | タイトル末尾に番号を付ける（例: `20260502-fix-auth`, `20260502-fix-auth-2`） |
| ステアリングを作ったが作業内容が大きく変わった | 新しいステアリングを作る（古い方は履歴として残す）。または requirements.md を更新して理由を明記 |
| 軽量で始めたが設計判断が必要になった | `index.md` の内容を `requirements.md` に流用しつつ、`design.md` `tasks.md` を追加して通常 steering に格上げ |
| 既存の作業途中で方針転換した | tasks.md に「方針変更」を明記、design.md にも追記 |

## 良いステアリングのチェックリスト

作成後、以下を満たしているか自己確認：

### 通常 steering
- [ ] requirements.md: 受け入れ条件が検証可能（「動く」ではなく「Xが起きたらYになる」のように具体的）
- [ ] design.md: 採用しなかった選択肢とその却下理由が書かれている
- [ ] tasks.md: タスクごとに完了条件が明記されている
- [ ] 並列実行可能なタスクが見分けられる

### 軽量 steering
- [ ] index.md が 3 行以内（長すぎたら通常 steering に格上げ検討）
- [ ] 「なぜ」が読者に伝わる（1 ヶ月後の自分が読んで分かるか）

# PR 作成スキル

コミット済みの変更からプルリクエストを作成する。事前品質チェック、構造化された PR 本文を生成する。

**重要**: まず以下 4 ファイルをすべて読み込むこと。
- `.claude/skills/workflow-config.md`（ブランチ戦略・PR 設定）
- `.claude/skills/workflow-conventions.md`（コミットメッセージ・PR タイトル規約）
- `.claude/skills/workflow-issues.md`（完了条件の更新手順）
- `.claude/skills/workflow-playbooks.md`（解決記録の振り返り・PR 本文の推奨セクション）

## 引数の解析

`$ARGUMENTS` からオプションを取得する。

- `--base <ブランチ>`: ベースブランチ（未指定の場合は `workflow-config.md` のデフォルトベースブランチを使用）
- `--draft`: ドラフト PR として作成

## 現在の状態

- 現在のブランチ: !`git branch --show-current`
- Git ステータス: !`git status --short`
- 既存の .steering: !`ls docs/.steering/ 2>/dev/null || echo "なし"`

## ワークフロー

### ステップ 1: 安全性チェック

1. 現在のブランチが保護ブランチ（`workflow-config.md` の「ブランチ戦略」に記載）でないことを確認する
   - 保護ブランチ上の場合はエラーを報告して停止する
2. ベースブランチに対してコミットが存在することを確認する
3. 未コミットの変更がないことを確認する
   - ある場合はユーザーに警告する

### ステップ 2: 事前品質チェック

CLAUDE.md の「ビルド・テスト・デプロイ」セクションに記載されたコマンド（lint・型チェック・テスト等）を実行する。

チェックが失敗した場合はエラー内容を報告し、修正してから PR 作成するか続行するかユーザーに確認する。

### ステップ 3: PR 情報の収集

1. `git diff <base>..HEAD` で変更内容を把握する
2. `git log --oneline <base>..HEAD` でコミット一覧を取得する
3. `docs/.steering/` 配下に関連する steering があれば参照する
4. ブランチ名から Issue 番号を抽出する（例: `feat/123-xxx` → `#123`）
5. diff から docs / CLAUDE.md 更新の要否を点検する。各 docs の役割は [`.claude/rules/docs-content.md`](../../rules/docs-content.md) を参照し、変更領域に対応する doc・`CLAUDE.md`（ディレクトリ構成図 / 進捗表）が更新されているか照合する。未更新の該当箇所があればユーザーに「更新するか / 対象外か」を確認する。

### ステップ 4: PR タイトルと本文の生成

#### タイトル形式（Conventional Commits 準拠）

`<type>: <簡潔な説明>` の形式でタイトルを生成する。type の一覧と用途は
[`workflow-conventions.md`](../workflow-conventions.md) の「Type 規約 / PR タイトル形式」を参照。

**例**:
- `feat: search_opportunities ツールを追加`
- `fix: SSE 切断時のリトライ処理を修正`
- `refactor: orchestrator の履歴管理をヘルパー関数に抽出`
- `docs: architecture.md に環境変数追加手順を追記`

不明な場合は最初のコミットメッセージを使う。複数の変更が混在する PR は **可能なら分割を推奨**、難しければ最も大きな変更の type を選ぶ。

#### 本文形式

[`references/pull_request_template.md`](references/pull_request_template.md) のテンプレートを使う。playbook ごとの推奨セクションは `workflow-playbooks.md` の各 playbook の「**PR 本文に推奨のセクション**」を参照。

### ステップ 5: ユーザー確認

生成した PR タイトルと本文をユーザーに提示し、以下を確認する:
- タイトル・本文の修正が必要か
- ドラフト PR にするか
- ベースブランチは正しいか

### ステップ 6: プッシュと PR 作成

```bash
git push -u origin <現在のブランチ>
gh pr create --title "タイトル" --body "本文" --base <ベースブランチ> --assignee @me
```

### ステップ 7: 関連 Issue の完了条件を更新

PR 本文に「Closes #N」がある場合、`workflow-issues.md` の **「完了条件の更新手順」** に従って Issue を更新する。

レビュー対応で達成状況が変わる場合は `/fix-review` で再更新する。

### ステップ 8: 解決記録の振り返り

# PR レビュースキル

`gh` CLI で PR の差分・コミット・既存コメントを取得し、レビュー観点でコードを精査した上で、ユーザー承認のもと PR にレビューコメントを投稿する。

**重要**: まず `.claude/skills/workflow-config.md` を読み込み、ブランチ戦略・レビュアー設定を取得すること。規約・playbook の参照が必要になった場合は、同ディレクトリ内の `workflow-conventions.md` / `workflow-issues.md` / `workflow-playbooks.md` を必要に応じて参照する。

## 引数の解析

`$ARGUMENTS` から PR 番号（数値）を取得する。未指定の場合は現在のブランチに紐づく PR を自動検出する。

## 現在の状態

スキル実行開始時に以下を取得する:

- 現在のブランチ: `git branch --show-current`
- リポジトリ: `gh repo view --json nameWithOwner --jq '.nameWithOwner'`

## ワークフロー

### ステップ 1: PR の特定

1. `$ARGUMENTS` に PR 番号がある場合はそれを使用する
2. 未指定の場合:
   ```bash
   gh pr view --json number --jq '.number'
   ```
3. PR が見つからない場合はエラーを報告して停止する

### ステップ 2: PR メタ情報の取得とセルフレビュー判定

```bash
gh pr view <PR番号> --json number,title,body,state,author,headRefName,baseRefName,url,additions,deletions,changedFiles,isDraft
gh api user --jq '.login'
```

- `state` が `open` でない場合は警告し、続行するか確認する
- ドラフト PR の場合は確認する
- PR タイトル・本文・作成者・変更規模をユーザーに提示する
- **セルフレビュー判定**: PR の `author.login` と現在のユーザー（`gh api user --jq '.login'`）を比較し、一致する場合は「セルフレビュー」として扱う
  - セルフレビュー時は後段の総合判定で `event` を `COMMENT` に **強制**する（`APPROVE` / `REQUEST_CHANGES` は GitHub 仕様で投げられないため）
  - その旨をユーザーに通知する

### ステップ 3: 変更ファイル一覧と差分の取得

```bash
gh pr diff <PR番号>
gh pr view <PR番号> --json files --jq '.files[] | {path,additions,deletions}'
```

変更ファイル数が多い場合（例: 20 ファイル超）はユーザーに以下を確認する:
- 全ファイルレビューするか
- 特定ディレクトリ・ファイルに絞るか

### ステップ 4: 既存レビューコメントの確認

過去のレビューと重複指摘を避けるため、既存のコメントを取得する:

```bash
gh pr view <PR番号> --json reviews,comments
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments
```

既に指摘済みの内容は再指摘しない。

### ステップ 5: 関連設計ドキュメント・規約の参照

レビュー基準を揃えるため、以下を確認する:

- `CLAUDE.md`（編集ルール・原則）
- `docs/` 配下の関連設計ドキュメント
- `docs/.steering/` の関連 steering（PR の変更領域に対応するもの）
- `.claude/rules/` 配下のルール

### ステップ 6: レビューの実施

以下の観点で各変更を精査する:

#### 必須観点

- **正確性**: ロジック誤り・例外処理漏れ・off-by-one・null/undefined ハンドリング
- **セキュリティ**: SQL インジェクション・XSS・認証/認可漏れ・シークレットの混入・入力検証
- **テスト**: 重要な変更にテストがあるか・テストが意味のある検証か
- **設計整合**: 設計ドキュメント・既存パターン・CLAUDE.md ルールとの整合性
- **可読性**: 命名・関数の責務・複雑度
- **パフォーマンス**: N+1・不要なループ・大きなオブジェクトのコピー
- **後方互換性**: 破壊的変更の有無と妥当性
- **docs / CLAUDE.md 整合**: 実装変更に対応する `docs/` の各ファイル（役割対応表は [`.claude/rules/docs-content.md`](../../rules/docs-content.md) を参照）と `CLAUDE.md` のディレクトリ構成図 / 進捗表が更新されているか（記述と実装の食い違い・古いコード例の残存等）

#### 任意観点

- ドキュメント更新の有無
- 命名規則の一貫性
- 不要なコメント・デッドコード
- 依存ライブラリの追加が妥当か

### ステップ 7: 指摘案の整理とユーザー確認

各指摘を [`references/comment-template.md`](references/comment-template.md) の **指摘テンプレート** に従って整理する。重大度ラベル（🔴 Critical / 🟡 High / 🔵 Medium / 🟢 Low）の定義も同テンプレートを参照。

整理した指摘群を以下の形でユーザーに提示する:

```
=== レビュー指摘案 ===

<指摘テンプレートで指摘 N 件>

総合判定案: comment / request-changes
全体コメント案: <要約>
```

ユーザーに以下を確認する:
- 各指摘を投稿するか / 却下するか / 修正するか
- 総合判定（request-changes / comment）
- 全体コメントの内容

### ステップ 8: レビューコメントの投稿

ユーザー承認後、`gh api` で PR レビューを作成する。

#### コメント本文の組み立て

全体コメント（`body`）は [`references/comment-template.md`](references/comment-template.md) の **全体コメントテンプレートの選択** 表に従って `pass-template.md` または `fail-template.md` を選び、プレースホルダ（`{{pr_author}}` `{{reviewer_name}}` `{{commit_sha}}`）を置換する。

#### 投稿前チェック

[`references/comment-template.md`](references/comment-template.md) の **投稿前チェックリスト** をすべて満たすことを確認する。1 つでも満たさない場合は投稿せず、組み立てに戻る。

#### 一括投稿（推奨）

`POST /repos/{owner}/{repo}/pulls/{pr}/reviews` でインラインコメントと全体コメントを一括投稿する:

```bash
gh api repos/{owner}/{repo}/pulls/<PR番号>/reviews \
  --method POST \
  --input - <<'EOF'
{
  "event": "COMMENT",
  "body": "<全体コメント>",
  "comments": [
    {
      "path": "src/auth/login.ts",
      "line": 42,
      "side": "RIGHT",
      "body": "<インラインコメント>"
    }
  ]
}
EOF
```

- `event`: `REQUEST_CHANGES` / `COMMENT`
- 範囲指定の場合は `start_line` / `start_side` も付ける
- `commit_id` は省略可（最新コミットに紐づく）

`heredoc` の JSON は `jq` で組み立てるか、一時ファイル経由で渡すと安全。

#### 投稿失敗時

`POST /reviews` は **1 レビューにつき 1 回だけ** 呼ぶ。422 が返ったら失敗した inline を `body` に移して 1 回だけ再 POST する。**コメント単位での再 POST はしない**（成功分が submitted review として確定し、削除できない）。

`Path could not be resolved` は path に非 ASCII / スペースが含まれる、もしくは差分外のとき出やすい。該当する指摘は最初から `body` に書く。

### ステップ 9: 完了報告

- PR 番号・タイトル（URL）
- 投稿した指摘: インライン N 件 / 全体 1 件
- 総合判定: request-changes / comment
- レビュー URL（`gh pr view <PR番号> --json reviews` から最新を取得）

PR 作成者向けに「`/fix-review <PR番号>` で対応できる」ことを案内する。

`pass-template` を使った場合は、完了報告でも「approve は GUI から」を改めて案内する（テンプレートのフッターと整合）。

## 注意事項

- 指摘は **断定ではなく根拠を添える**（仕様・規約・参考リンクを示す）
- 細かすぎる Low は数を絞る（多すぎるとレビューの主旨がぼやける）
- セキュリティ上の重大な懸念は最優先で報告する
- レビューコメントにシークレット・社内固有情報を書かない
- 既に他のレビュアーが指摘済みの内容は重複投稿しない
- フォースプッシュや作成者ブランチへの直接コミットは絶対に行わない
- approve / merge は人間が GitHub Web UI から行う運用とする

3. ステージングとコミットを実行する:


   - `git add -A` や `git add .` は使わず、ファイルを明示的に指定する

# コミット・PR 規約

各スキル（create-branch, create-pr, fix-review 等）が参照する Conventional Commits 準拠の規約。

## Type 規約（Conventional Commits）

Conventional Commits の type をプロジェクト全体で統一して使う。コミットメッセージ・PR タイトル・ブランチプレフィックスはすべて下の表を参照する。

| type | 用途 | ブランチプレフィックス |
|------|------|---------------------|
| `feat` | 新機能 | `feat/` |
| `fix` | バグ修正 | `fix/` |
| `refactor` | リファクタリング（機能変更なし） | `refactor/` |
| `docs` | ドキュメントのみ | `docs/` |
| `chore` | ビルド・ツール設定・メンテナンス・依存更新 | `chore/` |
| `test` | テスト追加・修正 | （`chore/` に含める） |
| `style` | フォーマット変更（機能変更なし） | （`chore/` に含める） |
| `perf` | パフォーマンス改善 | （`feat/` または `fix/` に含める） |
| `ci` | CI/CD 設定 | （`chore/` に含める） |

ブランチを切るのは主に上の 5 種（feat / fix / refactor / docs / chore）。`test` / `style` / `perf` / `ci` は単独でブランチを切らず、内容に近い親プレフィックスのブランチに含める。

## コミットメッセージ形式

```
<type>(<scope>): <subject>

<body>
```

- **scope**: 任意。変更対象のモジュールやコンポーネント名（例: `auth`, `api`, `ui`）
- **subject**: 変更内容の要約。日本語可。末尾にピリオドを付けない
- **body**: 任意。変更の背景や理由を記載

`<type>: <簡潔な説明>` の形式（scope 省略可）。type は上記表から選ぶ。

# Issue 規約

各スキル（create-issue, create-pr, fix-review 等）が参照する Issue 関連の規約。

すべての Issue（gh / Web UI / スキル等、作成方法を問わず）は以下のルールに従う。

## Issue 本文テンプレート

[`create-issue/references/issue_template.md`](create-issue/references/issue_template.md) を使う。

## Issue タイトル規約

- **親 Issue（Epic）**: `[Epic] <主題>`（`area:` は付けるが `parent:` は付けない）
- **子 Issue**: `<type>(<scope>): <内容>` の Conventional Commits 形式（type は [`workflow-conventions.md`](workflow-conventions.md) の表に従う）
- **実行順がある Epic の子**（任意）: `[N] <type>(<scope>): <内容>`

## ラベル体系

`area:` / `priority:` / `parent:` の 3 軸 + Epic 識別用の `epic` 単発ラベルで構成する。各 Issue は最低 `area:` 1 つを必ず付ける。

### epic（親 Issue 識別）— 親 Issue は必須・単一ラベル

`[Epic] ...` タイトル prefix を付けた親 Issue には `epic` ラベルも合わせて付ける。一覧画面で色タグによる即時識別を可能にし、`label:epic` で全 Epic を抽出できるようにする。

子 Issue には付けない（親子の役割分離）。Epic がクローズされた後もラベルは外さない（履歴保護）。

### area:（機能領域）— 必須・複数付与可

| ラベル | 用途 |
|---|---|
| `area:app` | `backend/` `frontend/` どちらも含むアプリケーションコード |
| `area:agent` | エージェントロジック（プロンプト・ツール・ReAct ループ） |
| `area:infra` | Terraform / Azure リソース / Docker |
| `area:ci` | GitHub Actions / pre-commit / lint 設定 |
| `area:docs` | `docs/` 配下の永続的ドキュメント |
| `area:meta` | `.claude/` 配下のルール・スキル・テンプレ改善 |

frontend / backend は分けない（境界判断の運用負荷を避ける。チャット機能は両方を同時に触る Issue が多数派という実情に合わせる）。複数領域にまたがる場合は該当 area をすべて付ける（例: ツール追加なら `area:app` + `area:agent`）。**3 個以上**付くようならスコープが大きすぎるサインなので分割を検討する。

将来 `area:app` 内が分厚くなったら `area:auth` `area:db` `area:eval` `area:frontend` `area:backend` 等の派生 area を追加してもよい。

### priority:（優先度）— 任意

- `priority:p0-critical` / `priority:p1-high` / `priority:p2-normal` / `priority:p3-low`

### parent:&lt;番号&gt;-&lt;短縮名&gt;（親 Issue 紐付け）— 子 Issue は必須

例: `parent:2-roadmap`, `parent:27-claude-tooling`

親 Issue 自体には付けない（`[Epic] ...` タイトル prefix で識別する）。

Epic がクローズされた後もラベルは原則残す（履歴保護: 過去の子 Issue を `parent:` で検索可能にするため）。年 1 回程度の棚卸しで明らかに不要なものを整理する。

### GitHub 標準ラベルとの併用

`bug` / `documentation` / `good first issue` / `help wanted` / `blocked` などは併用可。type（`feat` / `fix` / `chore` 等）は **ラベル化しない**（タイトル prefix + branch prefix で表現する）。

## ラベル付与の運用フロー

### 親 Issue（Epic）作成時

1. タイトルを `[Epic] <主題>` 形式にする
2. `epic` ラベル + 該当する `area:` ラベルを 1〜複数付ける（Epic 自体には `parent:` を付けない）
3. 子 Issue 用に `parent:<新 Epic 番号>-<短縮名>` ラベルを発行する:
   ```bash
   gh label create parent:<番号>-<短縮名> --description "Epic #<番号> の子" --color FEF2C0
   ```
   短縮名は Epic 内容を 1〜2 単語で表す英小文字（例: `roadmap`, `claude-tooling`）

### 子 Issue 作成時

1. タイトルを `<type>(<scope>): <内容>` 形式にする（`[Epic]` は付けない）
2. 親 Epic に対応する `parent:<番号>-<短縮名>` ラベルを付ける
3. 親 Epic の `area:` を初期候補として、子の作業範囲に応じて `area:` を選定（複数可、3 個以上は分割サイン）
4. [Sub-issues API](#sub-issues-api-の使い方) で正式な親子関係を設定する

## 子 Issue の運用

- 子 Issue リンク方式: タスクリスト（チェックボックス形式、GitHub Tracked Issues 連携）と [Sub-issues API](#sub-issues-api-の使い方) を併用する
- 大規模 Issue の分割提案: 完了条件が 5 項目以上、または複数ドメインにまたがる場合に提案する

## Sub-issues API の使い方

子 Issue を作成した後、以下の API で親 Issue に紐づける:

```bash
gh api repos/{owner}/{repo}/issues/{親Issue番号}/sub_issues \
  --method POST \
  -F sub_issue_id=$(gh api repos/{owner}/{repo}/issues/{子Issue番号} --jq '.id')
```

- リポジトリ情報は `gh repo view --json nameWithOwner --jq '.nameWithOwner'` で取得する
- `sub_issue_id` には Issue の数値 ID（`node_id` ではない）を指定する

## 完了条件の更新タイミング

Issue 本文の完了条件チェックボックスは以下のタイミングで更新する：

- **`/create-pr` 実行時**: 達成済みの項目をチェック → PR と一緒に状態を反映
- **`/fix-review` 実行時**: レビュー対応で達成状況が変わった場合に再更新
- **PR マージ時**: GitHub が「Closes #N」で自動クローズ（デフォルトブランチへのマージのみ）

## 完了条件の更新手順

PR が「Closes #N」で参照する Issue について、以下の手順で完了条件を更新する：

1. Issue を取得: `gh issue view <番号> --json body`
2. 完了条件のチェックボックスを精査
3. 各項目を以下のいずれかに更新する:
   - **対応済み**: `[x]` に変更。実装が原文と変わった場合は `**【代替実装】** ...` を補足
   - **部分対応**: `[ ]` のまま `**【部分対応】** 実施したこと / 残したこと` を補足（打消しなし）
   - **不採用**: `[ ]` のまま、**項目本文を `~~...~~` で打消し** + `**【不採用】** PR #<番号> の議論で〜と判断` を補足
   - **未対応**: そのまま（次回 PR で対応予定）
4. 更新内容をユーザーに提示し承認を得る
5. `gh issue edit <番号> --body "<新しい本文>"` で更新

## 環境変数の追加が伴う Issue

`.env.example` への追記は Claude が実施し、`.env` への反映はユーザーに依頼する（[`restricted-files.md`](../rules/restricted-files.md) 参照）。Issue の完了条件にこの分担を明示する。

# 目的別プレイブック

各スキル（create-pr, fix-review 等）が参照する作業フローと振り返り規約。

## 解決記録の振り返り

`/create-pr` と `/fix-review` の手順内で実行する。

本作業中に **記録すべき知見が発生していないか必ず立ち止まって振り返る**。Claude が独断で「記録不要」と判断してはならない。スキップする場合は理由を明示する。

### 振り返り対象の例

- 公式ドキュメントに反するパターンや見落としやすい制約に遭遇した
- 複数の選択肢から選んだ際の根拠（non-trivial な技術判断）
- 後続案件でも再遭遇しそうな問題と回避策
- ハマって時間を使った解決策

### 手順

1. 直近のコミット・差分・会話を再確認し、**記録価値のある知見の候補を列挙する**
2. 候補がある場合: ユーザーに「以下の知見について `/record-solution` を実行しますか？」と提案する
3. 候補がない場合: **「PR 本文や対応コメントに書いたから不要」と独断しない**。「振り返った結果、再利用価値のある知見はなさそうです（理由: ◯◯）」とユーザーに明示し、承認を得てから次へ進む

## 目的別プレイブック

すべてのプレイブックは下記の標準フローを踏襲する。各プレイブックは作業の性質に応じて特有の注意点・スキップ可能な工程を明示する。

```
/create-issue → ブランチ作成 → 実装 → コミット → /create-pr → /review-pr → /fix-review → GUI 上でマージ
```

### feat — 新機能追加

新しい機能・コンポーネント・API エンドポイント等を追加する場合。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）
2. `/create-branch` — `feat/<番号>-<簡潔な説明>`
3. `/create-steering` — 設計判断ありなら通常（requirements.md + design.md + tasks.md）／ なければ軽量（index.md）
4. 必要なら `tech-researcher` エージェントで技術選定の最新化（**API リファレンスや使い方が不確かな時もここで確認** — training data の古さ・幻覚を回避）
5. 実装 → 実装中に API シグネチャ・使い方が不確かな箇所が出たら `tech-researcher` で公式 docs を確認 → コミット（pre-commit が自動実行）
6. **実装単位ごとに `test-engineer` サブエージェントを呼び出し、テスト実行・カバレッジ確認・lint チェックを行う**。失敗時は提案された修正内容を確認し parent 側で適用する（subagent 隔離による context 汚染防止）
7. `/create-pr`
8. **別セッションで** `/review-pr <PR番号>`（第三者視点）
9. `/fix-review <PR番号>`（指摘対応）
10. GUI 上でマージ

**スキップ可**: 自明な機能（定数追加、軽微な UI 調整等）なら steering は軽量で OK。

**PR 本文に推奨のセクション**: 修正内容の概要図 / ファイル別の修正詳細 / エビデンス（UI 変更がある場合）/ 運用ドキュメント（環境変数追加がある場合）

### fix — バグ修正

バグレポート・リグレッション・既知不具合の修正。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）— **再現手順を含める**
2. `/create-branch` — `fix/<番号>-<簡潔な説明>`
3. `/create-steering` — 通常は軽量（設計判断なし）／ 大規模な修正なら通常
4. **失敗するテストを先に書く**（バグを再現させる）— `test-engineer` でテストが「期待どおり失敗する」ことを確認
5. 修正実装
6. **`test-engineer` サブエージェントでテスト実行・カバレッジ確認・lint チェック**。テストが通ることと、既存テストへのリグレッションが無いことを確認
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: typo / コメント修正 など自明な変更は Issue 不要、軽量 steering もスキップ可。

**PR 本文に推奨のセクション**: 再現手順 / 修正前後の挙動（エビデンスとしてログやスクショ）/ 再発防止策（テスト追加内容）

### chore — 設定・雑務

ディレクトリ構造、依存追加、CI 設定、ツール設定変更等。

**手順**:

1. `/create-issue`（または既存 Issue を選ぶ）
2. `/create-branch` — `chore/<番号>-<簡潔な説明>`
3. `/create-steering` — **複数の選択肢から選ぶ場合は必ず通常**（後で経緯を追跡可能にする）
4. `tech-researcher` で最新版・ベストプラクティス・公式 docs（API リファレンスを含む）を確認
5. 設定ファイル作成・更新（実装中に詳細仕様が不確かなら追加で `tech-researcher` を呼ぶ）
6. 実機動作確認（実行コマンドを tasks.md に記録）
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: lock ファイル更新のみ等の決まり切った設定なら steering は軽量。

**注意点**:

- pre-commit / CI 設定変更は **`pre-commit run --all-files` で全体検証**
- ツール選定は **`tech-researcher` で再評価**してから決定（半年〜1 年で陳腐化する）

**PR 本文に推奨のセクション**: 影響範囲（どのスキル・ツールが影響するか）/ 動作確認手順 / 運用ドキュメント（環境変数・設定変更がある場合）

### docs — ドキュメント変更

README、設計図、用語集、運用手順等の追加・更新。

**手順**:

1. （任意）`/create-issue` — 大規模な変更なら作る
2. `/create-branch` — `docs/<簡潔な説明>`（Issue なしなら番号も省略）
3. `/create-steering` — 通常スキップ。新規ドキュメント追加なら軽量
4. 編集
5. `/create-pr`
6. 別セッションで `/review-pr <PR番号>`
7. `/fix-review <PR番号>`
8. GUI 上でマージ

**スキップ可**: typo / リンク修正は Issue 不要、直接ブランチで OK。

**注意点**:

- **新規ドキュメント作成前に `.claude/rules/docs-content.md` の役割表を確認** — 既存 8 ファイルのいずれかに統合できないか検討

**PR 本文に推奨のセクション**: 該当ドキュメントへのリンク / 変更前後の対応関係（移動・分割した場合）

### refactor — リファクタリング

機能変更を伴わない構造改善・命名変更・モジュール分割等。

**手順**:

1. `/create-issue` — 範囲・狙いを明示
2. `/create-branch` — `refactor/<番号>-<簡潔な説明>`
3. `/create-steering` — **必ず通常**（設計判断ある）
4. **着手前に既存テストが通ることを確認**（ベースライン）— `test-engineer` でベースラインを取る
5. リファクタ実施
6. **`test-engineer` サブエージェントで既存テストが全部通ることを再確認**（機能変更なしの担保）。lint クリーンも合わせて確認
7. `/create-pr`
8. 別セッションで `/review-pr <PR番号>`
9. `/fix-review <PR番号>`
10. GUI 上でマージ

**スキップ可**: 1 ファイル内の単純な命名変更程度なら steering 軽量も可。

**PR 本文に推奨のセクション**: 修正内容の概要図（変更前後のアーキテクチャ）/ ファイル別の修正詳細 / テスト網羅性（既存テストが通ったことのエビデンス）

## 出力言語

特に指定がなければ **日本語** で出力する（このプロジェクトのドキュメントが日本語のため）。

## 任務の3原則

1. **捏造禁止** — URL・バージョン・価格・関数名を一切でっち上げない。不確かなら明示する
2. **二重ソース確認** — 価格・モデル可用性・破壊的変更等の重要情報は **必ず 2 つ以上の信頼できるソース** で確認する
3. **日付意識** — 情報がいつ書かれたかを記録し、「現時点で有効か」を判定する

## 調査の進め方

### Step 1: 何を調べるかを明確化

まず以下を整理する：

- 質問の本質は何か（事実確認 / 比較検討 / 推奨判断 / **API リファレンス参照** のどれか）
- いつの情報が必要か（最新の確定情報 vs 噂レベルでも OK）
- 比較対象がある場合、評価軸は何か（価格 / 速度 / 機能 / 信頼性）
- API リファレンス参照の場合、対象ライブラリのバージョンが明示されているか

### Step 2: プロジェクト前提を取得

`docs/` 配下のドキュメントから、このプロジェクトの **現在の技術選定** を把握する：

- `docs/product-requirements.md` — 要件・制約
- `docs/architecture.md` — 採用スタック・選定理由

「現在の選択を変える価値があるか」という観点で調査する。

### Step 3: 信頼できるソースを優先順位で当たる

| 優先度 | ソース |
|-------|--------|
| 最高 | 公式ドキュメント（採用クラウド / 採用 LLM プロバイダ / 公式 GitHub README 等） |
| 高 | 公式の価格ページ・リリースノート・Changelog |
| 中 | 開発元の公式ブログ・公式 Tech Talk スライド |
| 参考 | 信頼できる第三者ベンチマーク・OSS 比較サイト |
| 補助 | Stack Overflow / Reddit（補強情報のみ、一次ソースとして使わない） |

非公式チュートリアル・古いブログは一次ソースに使わない。

### Step 4: クロスチェック

価格・モデル名・破壊的変更等は **公式 + もう 1 ソース** で確認する。食い違いがあれば率直に報告する。

### Step 5: 結論ファースト で要約

詳細を並べる前に、**1〜2 文で結論** を出す。読み手が忙しい前提で書く。

```markdown
# [調査トピック] 調査レポート

## 結論
[1〜2 文で答え。推奨判断が必要なら「○○を推奨」と明示]

## 主な根拠
- [根拠 1（短く）]
- [根拠 2]
- [根拠 3]

## 比較表（必要時）
| 観点 | 候補 A | 候補 B | 候補 C |
|------|--------|--------|--------|

## 確信度
- [verified / likely / uncertain] のいずれかと、その理由

## 出典
- [タイトル](URL) — 公開日 / 確認日: YYYY-MM-DD
- [タイトル](URL) — 公開日 / 確認日: YYYY-MM-DD

## プロジェクトへの影響（あれば）
- 既存判断の見直しが必要か（具体的にどのファイルのどこ）
- 新たに検討すべき選択肢
```

### 拡張モード：Deep（明示的に依頼された時のみ）

Brief に加えて：
- 詳細な比較・トレードオフ分析
- 設定例・コードスニペット
- 既知の落とし穴・移行手順
- 代替案

## 確信度ラベルの使い分け

| ラベル | 意味 |
|-------|------|
| `verified` | 公式 2 ソース以上で一致確認済み |
| `likely` | 公式 1 ソース or 第三者複数で一致 |
| `uncertain` | 1 ソースのみ・推測含む・公開日が古い |

## API リファレンス参照モード

「API シグネチャ確認」「使い方の最小コード」等の実装支援系クエリでは、推奨判断より **正確な事実の抽出** が主目的。出力は Brief を簡略化した以下の構造で良い：

```markdown
# [ライブラリ名 / 関数名] リファレンス

## 結論
[シグネチャ / 最小使用例]

## 公式ドキュメント該当箇所
[タイトル](URL) — 公開日 / 確認日: YYYY-MM-DD

## 補足（あれば）
- 破壊的変更
- バージョン依存
- 既知の落とし穴
```

クロスチェックは「公式 docs + 公式 GitHub のソースコード or リリースノート」で十分。第三者ブログの API 例は採用しない（古い可能性が高い）。

## 推奨判断を出す時のルール

ユーザーが「どれが良いか」を聞いた場合、**中立な情報羅列で終わらず、推奨を 1 つ出す**。

判断軸：

- このプロジェクトの **コア要件**（`docs/product-requirements.md` のコア要件節）と整合するか
- 既存の技術選定との一貫性
- 切り替えコスト vs 切り替えメリット

「人によります」「ケースバイケース」は避ける。明確に推奨を 1 つ出した上で、別の判断が妥当なケースを補足する。

## やってはいけないこと

- ❌ URL を「たぶんこんな形式」で生成する → 必ず `WebFetch` / `WebSearch` で実在を確認
- ❌ バージョン番号・価格をうろ覚えで書く → 公式ページで再確認
- ❌ マーケティング表現の引用（「業界をリードする」等） → 具体的事実だけ取る
- ❌ 1 ソースで重要判断を下す → 必ずクロスチェック
- ❌ 「結論」を最後に書く → 必ず冒頭に
- ❌ 「ググりました」レベルの羅列 → 必ず推奨判断や評価を加える
- ❌ プロジェクトコンテキスト無視の汎用回答 → 必ず `docs/` を読んで整合性を判定

## 調査結果の保存（任意）

調査結果が将来の判断にも使える内容なら、ユーザーに **`docs/.steering/[YYYYMMDD]-[トピック]/index.md` への保存を提案** する。記録するかどうかはユーザーに判断を任せる（自動保存はしない）。

## 失敗時の振る舞い

公式ソースで確認できない時：

1. 何が確認できなかったかを **明示**
2. 代わりに何が確認できたかを **記載**
3. 次の調査手段を **提案**（GitHub Issues / リリースノート / 公式 Discord 等）
4. **推測値で穴埋めしない**

不明なものは「不明」と書く方が、誤情報を載せるより遥かに価値がある。

## 出力言語

## 任務の3原則

1. **実行責務に集中する** — テスト実行・カバレッジ確認・lint チェックのみを行う。コードの修正は提案のみで、`Edit` / `Write` 権限は持っていない（持たない設計）
2. **要約ファースト** — テストランナー / linter の生出力を貼らない。失敗テスト名・エラーメッセージ要点・推奨修正に絞る
3. **判断は親に委ねる** — 失敗の原因が「テストの誤り」「実装の誤り」「環境差」のいずれかは断定せず、根拠と仮説を提示する

- 「カバレッジレポートだけ整理して」
- 「lint 違反を整理して」
- 「外部 API 実呼び出しを伴うテストを動かして」

不明なら推測せずに親エージェントに確認する。

### Step 2: コマンド実行

1. 何が失敗したかを **明示**（コマンド・終了コード・主要なエラー行）

3. 親エージェントに依頼すべき次の手を **提案**（例: 「依存をインストールしてから再依頼してください」）

## 2. 記述形式の選択

### 2.1 Mermaid（原則）

設計書・要件書・steering ドキュメントの図は **原則 Mermaid を使う**。

- Markdown に直接埋め込める
- バージョン管理が容易（テキスト diff で差分が読める）
- ツール不要で編集可能
- GitHub・主要 IDE でレンダリングされる

### 2.2 ASCII アートを使ってよい例外

以下に該当する場合のみ ASCII 可：

| 例外 | 理由 |
|---|---|
| **ワイヤフレーム / 画面レイアウト** | UI のボックス配置を視覚的に表現するのに ASCII の方が直感的。Mermaid でも書けるが冗長になりがち |
| **ディレクトリツリー** | ファイル階層の表現は ASCII（`├──` `└──`）が業界標準 |
| **テキスト中心の依存方向図（矢印 1〜2 本）** | `api → agent → repositories` のような単純な関係。複雑になったら Mermaid に切替 |

上記以外の図（システム構成・状態遷移・シーケンス・ER 図・フローチャート等）は **Mermaid 必須**。

### 2.3 画像ファイル（最小限）

複雑なワイヤフレームやモックアップで Mermaid / ASCII では表現が困難な場合のみ：

- `docs/images/` フォルダに配置
- PNG または SVG 形式を推奨
- ファイル名は `[ドキュメント名]-[図名].png` のように紐付けが分かる命名

→ Mermaid に置き換える。複数経路・複数依存先がある時点で Mermaid のほうが読みやすい。

## 4. 章番号と見出し階層

### ルール

- **章番号は `## N. タイトル` / `### N.M サブタイトル` の階層のみ** 使う

- 章番号外の独立セクション（「コア」「概要」など）を最上位に置かない。`## N.` の階層に統合する
- `# H1` はファイル先頭のタイトル 1 個のみ

```markdown
### 1.1 目的
```

```markdown
## 1. 概要
```

## 7. TODO・未確定箇所の表記

### ルール

- **未確定箇所は引用 callout 形式** に統一: `> **未確定**: ...`

## 8. 強調・callout

### ルール

- **重要事項は引用 callout 形式**（`> **重要**: ...`）に統一

```markdown
> **重要**: distro と `FastAPIInstrumentor.instrument_app()` の併用は禁止。
```

```markdown
**重要**: distro と FastAPIInstrumentor の併用は禁止。   ← callout でない
```

## 9. コードブロックの長さ

# アクセス制約のあるファイルの取り扱い

Claude は以下のファイルへの **Read / Edit / Write、および Bash 経由の読み取り（`cat` / `head` / `tail` / `grep`）を実行できない**（[`.claude/settings.json`](../settings.json) の `permissions.deny`）。新規ファイル作成時もファイル名がパターンにマッチすると拒否されるため、**命名時にも注意**する。

## 対象ファイル

| パターン | 例 |
|---|---|
| `**/.env` `**/.env.local` `**/.env.development` `**/.env.staging` `**/.env.production` | 実値の入った環境変数ファイル |
| `**/*.pem` `**/*.key` | TLS / SSH 秘密鍵 |
| `**/credentials.json` | クラウド認証情報 |
| `**/*secret*` | ファイル名に "secret" を含む全ファイル |
| `~/.ssh/**` `~/.aws/**` | ホームディレクトリの認証情報 |

`.env.example` は **deny に含まれない**（テンプレファイルのため）。Claude が編集できる。

## 代替フロー

Claude は対象ファイルの実値を一切認識できない。**動作確認・テスト・デフォルト値の検証など、実値が関わる作業はすべてユーザー確認を必ず挟む**。設定ファイルのデフォルト値だけで判断・動作確認をしない。

### 値を書き込む必要があるとき

1. 書くべき内容をコードブロックで提示する
2. ユーザーに書き込みを依頼する（例: 「以下を `.env` に追記してください」）
3. 書き込み完了の確認をユーザーから得る

### 値を確認したいとき

1. **何を確認したいか・なぜ必要か** を明示する
2. ユーザーに値の提示を依頼する
3. 機密値そのものをコミット・ログ・PR 本文に残さない

## 環境変数を新規追加する作業

新しい環境変数を導入するときは：

1. **`.env.example` への追記は Claude が実施**（テンプレ更新）
2. **`.env` への反映はユーザーに依頼**（実値の書き込み）
3. 関連ドキュメント（`docs/architecture.md` の環境変数表など）も同時に更新する

## 新規ファイル名の検査

`.claude/rules/`, `docs/`, ソースコード等で新規ファイルを作成する前に、ファイル名が deny パターン（特に `**/*secret*`）にマッチしないか確認する。マッチする場合は別名にする。

        uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          # ローカルスキル `.claude/skills/review-pr/` をレビューの単一ソースとして参照する。
          # スキルの観点・指摘テンプレート・投稿手順を更新すれば、本ワークフローにも自動反映される。
          # スキルが必要とする gh / git 系コマンドを allowlist に追加（デフォルト権限では拒否される）
          claude_args: |
            --allowed-tools "Bash(gh:*),Bash(git:*),Read,Glob,Grep"
          prompt: |
            PR #${{ github.event.pull_request.number }} をレビューしてください。

            レビュー観点・指摘テンプレート・投稿手順は `.claude/skills/review-pr/SKILL.md` に従ってください。
            特に以下を遵守:
            - Step 5「関連設計ドキュメント・規約の参照」（`CLAUDE.md` / `docs/` / `.claude/rules/` を確認）
            - Step 6「レビューの実施」の必須観点（正確性 / セキュリティ / テスト / 設計整合 / 可読性 / パフォーマンス / 後方互換性）
            - Step 8「レビューコメントの投稿」の手順（`pass-template` または `fail-template` を必ず選択）
            - 指摘テンプレート・重大度ラベルは `.claude/skills/review-pr/references/comment-template.md` に従う

            CI 自動実行の制約:
            - Step 7 のユーザー確認ステップはスキップし、整理した指摘をそのまま投稿してください
            - Step 2 のセルフレビュー判定は適用してください（`event` の決定に必要）
