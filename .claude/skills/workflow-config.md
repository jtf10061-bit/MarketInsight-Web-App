# ワークフロー設定

各スキル（create-issue, create-pr, fix-review 等）が参照する共通設定。プロジェクト固有の設定値はこのファイルで一元管理する。規約・playbook は領域別の別ファイル（後述）を参照。

## GitHub 操作のツール選択

- GitHub 操作（Issue、プルリクエスト、リポジトリ等）には **`gh` CLI を使用する**こと
- MCP ツール（`mcp__github__*`）は使用しない
- ローカル Git 操作には `git` コマンドを使用する

## 完了時の次ステップ提案

各スキルは完了報告時に、次のアクションを提案すること。

| 完了したスキル | 提案する次のアクション |
|--------------|---------------------|
| `/create-issue` | `/create-branch --issue <作成した Issue 番号>` で作業ブランチを作成 |
| `/create-branch` | `/create-steering` で作業計画（steering）を作成 |
| `/create-hotfix-branch` | 復旧に必要な最小修正をコミットし、`/create-pr` で main 向け PR を作成 |
| `/create-steering` | 実装を進める（draft PR は作成済み）。完了したら `/create-pr` で ready に昇格 |
| `/create-pr` | `/review-pr` でレビュー、または `/fix-review` でセルフレビュー対応 |
| `/review-pr` | PR 作成者に `/fix-review <PR番号>` での対応を案内 |
| `/fix-review` | 追加の指摘があれば再度 `/fix-review`、approve をもらえていれば GUI 上でマージ |

## 自動起動時の運用ルール

`/create-issue` / `/create-branch` / `/create-steering` の 3 スキルは、ユーザーが slash command を打たなくても自然言語入力から自動起動する。自動起動時は以下を必ず守ること（明示起動でも同じ規律で動作する）。

### 1. 起動宣言

スキル開始時の最初の発話で、次の形式で必ず宣言する：

> `/<skill 名>` を起動します（検出意図: <ユーザー発話のうち、起動判断の根拠になった部分>）

ユーザーが「何が起きているか」を即座に把握できるようにする。

### 2. 確認ステップの厳守

各 SKILL.md の「ユーザー承認を得る」「ユーザーに提示して確認する」ステップは **絶対に省略しない**。自動起動だからといって暗黙に進めてはならない。

### 3. 安全チェック失敗時の停止

各 SKILL.md の事前チェック（未コミット変更の検出・同名ブランチの検出・保護ブランチの検出等）で問題を検出した場合は、**即座に停止しユーザーの判断を仰ぐ**。自動的に回避策を実行してはならない。

### 4. 曖昧入力時の確認

ユーザー発話から起動判断が曖昧な場合（例:「計画立てて」が `/create-steering` を指すのか、概念的な議論を求めているのか不明な時）は、起動前に次の確認を入れる：

> `/<skill 名>` を起動しようとしていますが、よろしいですか？（no で説明や別アプローチに切り替えます）

### 5. 連鎖時の入力待ち厳守

スキル末尾の「次スキル提案」で yes 受領 → 次スキル起動は OK だが、**起動後の最初の対話的ステップ（タイトル確認・ブランチ名提示等）でユーザー入力を必ず待つ**。連鎖でユーザー確認をスキップしてはならない。
